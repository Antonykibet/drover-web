# Drover Profit — landing page

Static marketing / waitlist page for **Drover Profit**: project profitability for design studios,
plus a small API that stores waitlist sign-ups in Postgres.

## Structure

```
index.html          # the whole page: design tokens, components, markup, waitlist script
shots/              # photography and product screenshots used on the page
Dockerfile          # nginx:alpine serving index.html + shots/
nginx.conf          # caching, security headers, gzip, real 404s
api/                # waitlist API (Go): POST /api/waitlist, GET /api/health
deploy/             # VM side: setup script, deploy/logs/export commands, compose file
.github/workflows/  # CI: asset check, image build, smoke test, deploy on main
```

No build step. Open it locally with any static server:

```sh
python3 -m http.server 8000
# then visit http://localhost:8000
```

Or the production container: `docker build -t drover-web . && docker run --rm -p 8080:80 drover-web`.

The waitlist form posts to `/api/waitlist` on the same origin, so a plain static
server shows the page but can't save sign-ups. The API's tests run without a
database:

```sh
cd api && go test ./...
```

## Waitlist

`POST /api/waitlist` takes JSON `{email, size, tool}`, validates it, and stores
it in the `waitlist` table (`email, size, tool, created_at`). It answers `204`
on success, also for an address already on the list (matched
case-insensitively, the first sign-up is kept), so the form can't be used to
probe who signed up. Errors are `400 {"error": "invalid_email" | "invalid_size"
| "invalid_tool" | "bad_request"}`, `415` for non-JSON and `429` after 5 tries
from one visitor in 10 minutes.

- **Bots**: a hidden `website` field; anything in it gets a `204` and is dropped.
- **Privacy**: addresses never go to the logs, and visitor IPs only key the
  in-memory rate limit, never stored.
- **Reading the list**: `ssh drover@<host> sudo drover-waitlist-export > waitlist.csv`.

## Deployment

Runs on the VM as three containers behind Traefik, which terminates TLS with a
Let's Encrypt certificate (`le` resolver):

- `drover-web`: nginx serving the page. `www.<domain>` permanently redirects to `<domain>`.
- `drover-api`: the waitlist API. Traefik routes `<domain>/api/*` to it.
- `drover-db`: Postgres 17, on a private network only `drover-api` joins. Data is
  in the `drover-web_drover-db-data` volume; credentials are generated by the
  setup into `/etc/drover-web/db.env` (root-only).

Every push runs CI: it checks every `shots/` image the page references exists,
builds the image and smoke-tests it; a second job tests the API, builds its
image and smoke-tests it against Postgres. A push to `main` then SSHes to the VM
as the `drover` user, whose key can only run `drover-web-deploy`: it pulls `main`
into `/srv/drover-web`, builds both images, restarts the containers and fails
unless all three report healthy. Repository secrets: `VM_HOST`, `VM_USER` (`drover`), `VM_SSH_KEY`.

### The `drover` user

`drover` has no sudo or docker group. Through sudo it can run exactly three
root-owned commands:

```sh
sudo drover-web-deploy       # deploy main now
sudo drover-web-logs [-f]    # page container logs
sudo drover-waitlist-export  # waitlist as CSV on stdout
```

API logs are in Grafana (Loki, `stack="drover-web"`).

What the VM runs is fixed by root-owned files, not the repo: the compose file
(volumes, network, Traefik labels) is `/etc/drover-web/compose.yml`, and a deploy
refuses an image that sets its own `traefik.*` labels. Commits change the page
and its image, never routing or host access. Changes under `deploy/` take effect
only when root re-runs the setup.

### First-time setup on the VM

As the admin user, make a key for CI and run the setup as root:

```sh
ssh-keygen -t ed25519 -N '' -C gh-actions-deploy@drover-web -f ~/.ssh/drover_web_deploy
sudo bash deploy/setup.sh <domain> ~/.ssh/drover_web_deploy.pub [people.pub]
```

`people.pub` holds the public keys that get a shell as `drover`. The setup is
re-runnable and rewrites `drover`'s `authorized_keys` from its arguments each
time. Put the private key in the `VM_SSH_KEY` secret, and point `A` records for
the domain and `www.` at the VM before the first deploy.

## Notes

- All styling resolves to CSS custom properties defined in `:root` (the "Drover design system v2").
- The waitlist database has no automated backup yet. A one-off dump:
  `docker exec drover-db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > drover-$(date +%F).sql`.
